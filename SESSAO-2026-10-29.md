## 5. Como rodar localmente

O Postgres embutido (porta 5433) e o servidor (porta 3001) caem quando a sessão fecha. Para subir de novo:

```powershell
Set-Location "$env:TEMP\bdsgp-pg"; node start.mjs
```

Depois, no projeto, suba o servidor de desenvolvimento na porta 3001 (`preview_start` com `bdsgp-dev` no app, ou `npm run dev`).

Login de demonstração (dados do seed): `admin@demo.local` / `admin123`.

## 6. O que falta (deploy na nuvem)

Bloqueio: o usuário precisa trocar `SENHA_DO_BANCO` nas duas linhas do `nuvem.env`. Se a senha tiver `@ # / ? % :`, trocar por `%40 %23 %2F %3F %25 %3A`. Senha esquecida: Project Settings > Database > Reset database password no painel do Supabase.

Depois, nesta ordem:

1. `prisma db push` com a `DIRECT_URL` (`schema=bdsgp`) para criar as tabelas.
2. `npm run db:seed` apontando para a nuvem.
3. `npx tsx prisma/copiar-catalogo.ts` (18.064 linhas).
4. Adicionar `DATABASE_URL` (pooled) ao ambiente de produção da Vercel, sem imprimir o valor.
5. `vercel deploy --prod`.
6. Testar a URL pública e o login.
7. **Trocar a senha `admin123`** do usuário de demonstração.
8. Rodar os advisors de segurança do Supabase depois que as tabelas existirem.

## 7. Riscos e limites conhecidos

- Documento acima de 4 MB é recusado; o arquivo fica dentro do banco (cresce o tamanho do Postgres).
- Atualização do catálogo em segundo plano é cortada em 60 s na nuvem. Se o download passar disso, o caminho é mover para uma fila (comentário `shortcut:` no código).
- O plano gratuito da Vercel tem limite de 60 s por função; buscas lentas no PNCP podem estourar.
- O usuário `admin@demo.local` com `admin123` não deve ir para um ambiente público sem troca de senha.
